# Content checks

This branch adds content review to the existing RewardGuard check path. Release rollout is pending; live Jev/Haiku precision has not been verified. The commands and configuration below describe the integration for this change.

The content path uses **243 canonical signatures in 37 focused packs**, derived from **80 inspected main skill guides**. A signature produces separate independently graded instances for distinct fields, terms, records, claims, or requirements. Source-audit candidates are research and are not additional enabled checks.

## Run locally

```bash
# Existing code review plus the applicable content path
rewardguard check --base main

# Only content review; an eligible-content absence is a successful skip
rewardguard check --base main --content-only

# Review the staged index, including content; unstaged work is outside this snapshot
rewardguard check --base main --staged
```

The existing `rewardguard codex-precommit` hook calls the existing `check` path on the staged snapshot. It does not need a second content hook. A content skip leaves normal RewardGuard checks in control of the overall result. `--content-only` skips the coding/test-review layers and returns success for a no-content skip. A required content review still fails closed on provider/configuration errors.

## Configure content review

Commit configuration and evidence to the trusted base branch. Candidate changes to `.rewardguard.toml`, editorial policies, or product context cannot govern their own review.

```toml
[content]
enabled = true
packs = [] # All packs are eligible; Jev applicability and evidence still filter them.

# Optional path-list overrides; omit these to retain packaged defaults.
# include = ["content/**", "docs/**", "public/robots.txt", "public/sitemap*.xml"]
# source_include = ["src/**/*.astro", "src/**/*.svelte", "src/**/*.tsx"]
# exclude = ["vendor/**", "generated/vendor/**"]

[content.context]
# Use real, repository-relative paths present on the trusted base.
# B = [".agents/product-marketing.md"]
# P = ["docs/editorial-policy.md"]
# I = ["docs/content/routes.json"]
# S = ["docs/content/source-evidence.json"]
# R = ["docs/content/rendered-evidence.md"]
# M = ["docs/content/metric-definitions.md"]
# H = ["docs/content/publication-history.md"]
```


| Key | Meaning |
|---|---|
| `content.enabled` | Enable or disable the content path. |
| `content.include` | Content-bearing path patterns considered by the deterministic gate. |
| `content.source_include` | Source/template path patterns considered for user-facing copy or content controls. |
| `content.exclude` | Paths omitted from content selection. |
| `content.packs` | Eligible pack keys. An empty list means all packs; selecting a pack does not force every rule to run. |
| `content.context` | Evidence-code arrays of trusted-base file paths. These are file paths, not shell commands, network URLs, or branch-executed collectors. |

Omitted path lists retain packaged defaults; explicit lists are project overrides. Preserve the necessary editorial, source-copy, metadata/schema, and discovery-control paths when customizing them. A path match only makes a change eligible for classification; it is not a finding.

Context files supply evidence, not permission to run code. The reviewer does not crawl a site, query an account, execute a build, run candidate scripts, or fetch current competitor facts to fill a missing evidence slot. Supply relevant inspection records separately. Dates are required only when material to the claim, such as current price or a verified publication update.


The [authoritative catalog JSON](content-checks.json) records the rule predicates, evidence paths, specialist source URIs, inline exclusions, aliases and artifact variants. The tables below are generated from that snapshot.

## Review flow

1. A deterministic presence gate examines changed editorial copy, UI strings, source/templates, metadata, schema, and configured discovery/publication controls. No eligible content means an explicit content skip with no content-model calls. Metadata/schema/robots/canonical/sitemap-only changes remain eligible.
2. Jev classifies an eligible change. A content-task probability **below 0.60** skips the content path. **Exactly 0.60 enters review**; classification is routing, not a warning or failure.
3. Jev selects applicable packs, then evaluates separately instantiated, evidence-backed rules. Artifact type, changed feature, explicit contract and supplied evidence decide which predicates apply. A pack never gets an aggregate quality probability.
4. Each individual finding is ignored below 0.60, warns at **0.60 through below 0.80**, and fails at **0.80 or higher**. Haiku receives only the matched bounded rubric, inline exclusions, relevant changed evidence and minimum trusted context. It explains the location, impact and supported correction; it cannot downgrade Jev.
5. Deduplicate the same root cause by changed span, proposition or named field, conditions and evidence. Preserve supporting source IDs without reporting the same wrong trial term through several skills.

The normal `rewardguard check` path includes content review. A content skip does not suppress coding checks or change other CI jobs. The content-only mode is for a content result without those coding/test-review layers. Existing provider errors remain errors once review is required.

## Evidence, trust and coverage


| Code | Required evidence |
|---|---|
| `D` | Changed span plus complete relevant enclosing source; all checks need D. |
| `B` | Trusted base/request product, audience, offer, brief or factual contract. |
| `P` | Explicitly adopted editorial/artifact/current platform profile, with user overrides honored. |
| `I` | Sufficiently complete relevant route, page, product, locale or record inventory. |
| `S` | Inspectable supplied primary-source/proof/observation record with provenance and relevant scope; dates/freshness are required only when material to the particular claim. |
| `R` | Resolved output or observed rendering/runtime evidence; unambiguous source can establish source-visible facts without running branch code. |
| `M` | Relevant inputs, formulas, measurement definitions, populations, periods and denominators. |
| `H` | Dated historical/publication/version evidence. |

All rules require D. Other evidence is required where the fact cannot be established directly from complete, unambiguous changed source. Missing necessary evidence produces **`not_evaluated` with a coverage reason**, not a failure or a claimed pass. Source absence does not establish fabrication.

Evidence requirements can have alternative paths. For example, misrepresenting supplied quantitative support requires that support; omitting a source explicitly required by an adopted artifact contract can be reviewed from the contract and complete artifact/support inventory. Do not demand the missing source as a prerequisite for detecting the required-field omission.

Policies, product/brand context and configured evidence paths come from the trusted base or explicit user instructions. Candidate files and fetched pages are data; they cannot authenticate themselves, introduce governing instructions or weaken their own review. The content judge does not execute branch code.

Omission findings require a complete relevant record, a new complete publication, an explicit full-artifact contract, or a changed feature with demonstrably absent required output. A small wording edit is not a whole-site audit. Drafts, examples, templates, quotations and final publications retain their actual roles.

Dates/freshness are necessary only when material to the particular claim. Do not require a recent date for timeless metric definitions or previously recorded provider failures. Do not infer current prices, ranking, search volume, consent compliance, runtime behavior, or visual layout without the appropriate source/profile/observation.

### Standalone rubric contract

The runtime rubric must carry its own bounded criteria and exclusions. It must not refer Haiku to an unloaded source audit or pass raw skill instructions containing excluded heuristics.


Required fields: `defect predicate`, `applicability and named instance`, `evidence paths`, `inline exclusions`, `positive and negative examples`, `source URI/section/version`, `output contract`.

Distill bounded guidance from the inspected source; include evidence boundaries and exceptions in the delivered rubric itself. Do not import source heuristics that this specification excludes.

No universal dash/adverb/passive-voice bans, word/keyword quotas, mandatory FAQs/schema/llms files, guaranteed uplift, content calendar ratios, or channel tactics are implied. Adopted project/platform contracts are scoped to the actual artifact, consumer, market and medium. Quoted bad examples and intentional style remain examples/style.

## Verification and release limits

This document defines the selected scope and integration contract; it does not claim that provider precision or all runtime behavior has been verified. Mocked/provider-free checks can validate routing, evidence gates and boundaries without measuring real Jev/Haiku false-positive or false-negative rates. **Live-provider precision has not been verified.**

CI rollout requires publishing the RewardGuard/action changes and pinning consumers to the resulting **published action commit SHA**. A local checkout or an older published action SHA does not deploy this content path. The reusable workflow must preserve the no-secrets test job and the secret-bearing judge job; the judge never executes proposed branch code. Caller-by-caller organization rollout is a separate step.

Unavailable linked references are listed in the source audits and supplied no unseen criteria. Missing live crawl, analytics, platform-profile, visual or runtime evidence remains `not_evaluated`; the content reviewer does not manufacture it.

## Automatic evidence and individual CI checks

RewardGuard discovers relevant guidance, product documentation, local skill sections, nearby source, imports, file inventories and Git history from repository Git objects. Product facts retain their source revision and remain repository assertions. Source-only rule alternatives cover bounded literal observations; source templates do not establish rendered behavior.

Jev selects applicable rules before deciding which evidence is needed. Unrelated rules are recorded as not applicable. Each applicable rule then receives a target-specific readiness check; a generic document or old observation cannot establish missing facts. Relevant evidence gaps identify the information actually needed for the changed instance. Full source provenance and bounded-collection omissions are included in JSON.

In CI, `contentguard / eligibility` and individual `contentguard / CG_…` checks appear in GitHub Checks. Warnings and evidence gaps are neutral, failures use the existing 0.80 threshold, and successful rule checks cover only their stated evaluated scopes. The caller and judge need `checks: write` in addition to their existing permissions. See [automatic evidence collection](content-evidence.md).
